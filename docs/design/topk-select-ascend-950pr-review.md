# TopKSelectFwdOp 昇腾 NPU 950PR 适配方案审核意见

审核日期：2026-10-28  
审核对象：[TopKSelectFwdOp 昇腾 NPU 950PR 适配方案](./topk-select-ascend-950pr-plan.md)  
审核方式：仓库静态代码核验与在线资料核验  
审核限制：未在 NPU 950PR 上进行编译、运行或性能实测

## 1. 审核结论

**当前方案需要重大修改后重新评审，不建议按现稿直接进入完整实现。**

该结论不是否定“外部后端 + TileLang Ascend 优先、Ascend C 备选”的总体方向，而是认为现稿仍属于调研提纲，尚未在以下方面形成闭环：

1. 公共契约中的跨调用确定性被误读；
2. 分块候选合并没有完成片上/全局内存、合并层数和布局设计；
3. TileLang 路线缺少对现有 TopK Selector 示例及实际依赖冲突的核验；
4. `torch.compile(fullgraph=True)` 没有进入明确的最终验收门槛；
5. MFU ≥95% 仍缺少公式、峰值依据和计时范围；
6. 特殊值、反向窗口和后端缓存职责仍需按现有实现澄清。

在上述问题关闭前，不应把方案中的阶段 4、阶段 5 视为可执行的实施和验收计划。

## 3. 分级审核意见

## 3.1 阻塞：跨调用索引集合稳定性是现有契约，不是待确认事项

### 方案现状

方案第 3 节和最终验收表将“同分候选是否要求跨次调用索引集合稳定”列为待确认事项。

### 代码依据

`TopKSelectFwdOp` 文档明确说明：

> Two calls on one input select the same positions, though a position may appear in a different slot.

manifest 同样要求：

> repeated calls on one input select the same set of positions, but a position may appear in a different slot.

因此，该约束适用于包括同分输入在内的所有有效输入，只允许槽位排列不同，不允许选中位置集合变化。

### 风险

分块截断、多核调度和无序 TopK 都可能在第 K 名存在同分元素时选择不同绝对索引。即使每次选中的分数完全相同，也仍然违反公共契约。

现有 `TopKSelectWorkload` 先收集分数、排序后比较，因此无法发现此类错误。

### 必须修改

1. 将该要求改为已确定的公共契约，不得继续留作可选语义。
2. 给出确定性选择规则，例如以分数和绝对索引构成全序；若采用其他规则，必须证明其结果与分块大小、核间调度和输出槽位顺序无关。
3. 说明该规则如何贯穿块内选择、候选合并和最终输出。
4. 增加以下测试：
   - 第 K 名附近存在大量同分元素；
   - 整行或整个有效窗口全部相等；
   - 同分元素跨越多个分块；
   - 相同输入重复调用；
   - 不同合法分块或调度配置。
5. 测试除现有分数多重集合比较外，还应比较重复调用之间排序后的索引集合。公共契约并不要求无序输出必须与 `torch.topk` 的索引排列完全一致。

## 3.2 阻塞：分块候选合并缺少资源与数据流闭环

### 方案现状

方案提出“块内 TopK + 全局合并”，但没有确定块大小、候选存储位置、合并层数、临时空间和 `G > 1` 的数据布局。

### 在线资料中的直接约束

Ascend C TopK 文档列出了以下约束：

- 仅支持沿输入最后一维选择，最多支持二维输入；
- Normal 模式要求 `inner <= 4096`；
- 要求 `k <= n`；
- 需要额外临时空间；
- 不同模式支持的数据类型和 `k` 范围不同。

这意味着：

- `L=16384/65536` 不能直接作为单次 Normal TopK 的 `inner`；
- 短窗口必须保留直接输出路径，不能无条件调用 `k <= n` 不满足的 TopK；
- `G > 1` 时固定 `(b,s,g)` 的 KV 数据在原输入中跨步分布，需要明确 gather、转置、复制或自定义索引数据流。

### 候选规模问题

以下计算仅以 `C=4096` 为例，用于暴露现稿遗漏的规模问题，并不预设最终块大小。每个候选按 FP32 分数和 int32 索引共 8 字节计算：

| 工作负载 | 分块数 | 每行首轮候选数 | 每行首轮候选空间 |
| --- | ---: | ---: | ---: |
| Prefill，K=1024 | 16 | 16384 | 128 KiB |
| Prefill，K=2048 | 16 | 32768 | 256 KiB |
| Decode，K=2048 | 4 | 8192 | 64 KiB |

如果 Prefill 的首轮候选全部写回全局内存，仅首轮候选就约为：

- K=1024：`16384 × 8 × 32768 = 4 GiB`；
- K=2048：`32768 × 8 × 32768 = 8 GiB`。

上述数值还没有计入后续合并层、源数据、API 临时空间和同步开销。如果不写回全局，则必须证明单行候选及其他缓冲区可以满足目标设备的片上存储预算。

### 必须修改

为三个 manifest 工作负载分别补充：

1. 块大小及其选择依据；
2. 每轮候选数量和合并树层数；
3. 每轮输入、输出及临时缓冲的位置和大小；
4. 单核、单行和整算子的峰值临时空间；
5. 片上存储不足时的全局工作区方案及所有权、生命周期；
6. 多核分片时的同步和确定性保证；
7. `G=1` 与 `G>1` 的地址映射和布局处理；
8. 空窗口、短窗口和尾块在每轮中的处理方式。

在完成该资源表之前，不能判断“块内 TopK + 全局合并”是否是可落地的默认基线。

## 3.3 高：TileLang 路线遗漏了现有 TopK Selector 示例及其实际限制

### 新核验事实

`tilelang-ascend` 仓库已提供：

`examples/topk_selector/example_topk_selector.py`

该示例比仓库首页和目标文档更直接相关，但不能直接作为本任务已经可行的证据：

1. 示例将整行 N 个分数放入 UB 后调用一次 `T.tile.topk`；
2. 示例参数说明指出，192 KiB UB 下 N 最大约为 8192；
3. 示例的验证只要求索引匹配率大于 0.99，而本任务要求精确语义验证；
4. 示例没有覆盖窗口、短窗口填充、跨调用确定性、绝对索引和 `G>1`。

因此，该示例应作为第一阶段的最小实验起点，同时必须明确其与本任务之间的差距。

### 依赖问题

本仓库固定 `tilelang==0.1.12`。`tilelang-ascend` 是专用变体，不能仅将兼容问题表述为“是否升级到 0.1.15”。

必须核实：

- 构建和运行使用的准确 commit；
- 生成的 Python 包名称、导入名称和版本；
- 与本仓库 `tilelang==0.1.12` 的依赖解析是否冲突；
- CANN、torch、torch-npu、Python 的版本组合；
- 950PR 是否被该组合实际支持；
- `T.tile.topk` 及所需 pass config 是否存在且可用。

### 必须修改

增加第一阶段 go/no-go 矩阵，至少包含：

| 项目 | 必须记录的结果 |
| --- | --- |
| 源码版本 | TileLang/TileLang-Ascend 的准确版本或 commit |
| 系统环境 | Python、CANN、torch、torch-npu、固件/驱动 |
| 包兼容 | 包名、导入名、与当前锁定依赖是否冲突 |
| 编译 | 最小 TopK 是否可离线编译 |
| 运行 | 是否可在 950PR 执行 |
| 正确性 | 是否通过本任务精确验证，而非示例的 99% 匹配 |
| 规模 | 可支持的 N、K、窗口和 G 范围 |
| 回退条件 | 何种失败必须切换到 Ascend C |

不得仅凭较新版本在线文档推断当前锁定版本或专用变体已经支持目标设备。

## 3.4 高：`torch.compile(fullgraph=True)` 必须进入最终验收

### 方案现状

方案提出先验证 eager，再检查 `torch.compile`，但最终验收表没有将其列为明确的通过条件。

### 代码依据

项目 README 对符合调用条件的算子承诺 `torch.compile(fullgraph=True)`，而 `Op.__call__` 的编译路径会直接调用目标 kernel。外部后端实现因此必须能够被该路径支持。

### 必须修改

若继续维持“保持现有公共接口”的目标，最终验收必须包含：

1. 冷调用 `torch.compile(op, fullgraph=True)`，无图断裂；
2. 编译路径输出通过完整 workload 正确性验证；
3. eager 与编译路径均进入预期后端；
4. 如存在 compile 缓存，验证首次和重复调用均正确。

不继承 CUDA Graph 承诺是合理的，但不能据此省略 `torch.compile` 验收。

## 3.5 高：MFU ≥95% 尚未形成可计算的验收标准

### 方案现状

方案正确避免了在缺少公式时直接宣称能够达到 95%，但仍将“MFU ≥95%”保留为最终目标。

### 问题

在以下内容明确之前，该目标不可验收：

- 分子采用比较次数、硬件指令次数还是其他 FLOP 定义；
- 分母采用 950PR 的哪一种峰值及其官方依据；
- 比较操作与该峰值是否属于可比较的运算类别；
- 计时只包含 kernel，还是包含候选写回、多核同步和公共 Op 调用；
- 逐工作负载达标还是汇总达标。

仓库已有 `topk_select_roofline`，其中按每个有效分数一次比较计数，并计算窗口读取、窗口元数据和输出字节。方案应明确是复用、修正还是拒绝该定义。

### 必须修改

1. 写出 MFU 的完整公式和各项单位；
2. 给出峰值来源、计时边界及统计方法；
3. 说明 95% 的适用工作负载；
4. 同时报告三个 manifest 工作负载的延迟、有效带宽和峰值临时空间；
5. 如果 MFU 定义无法在实现路线选择前确定，应将其列为阻塞项，不能默认进入性能验收。

## 3.6 中：特殊值与反向窗口应按现有语义收敛

### `starts > ends`

现有参考实现通过有效范围掩码将其处理为空窗口，roofline 也使用 `max(0, end-start)`。因此，若目标是保持现有语义，默认应返回与 `seq_len=0` 相同的全 `seq_len_kv` 填充结果，而不是重新开放为可报错或其他行为。

### NaN、无穷和正负零

当前 manifest 对 FP32 logits 没有声明排除这些值。方案可以补充显式契约，但不能由后端自行选择支持或拒绝：

- 若继续支持完整 FP32 输入域，应根据参考实现定义并测试相关行为；
- 若准备限制输入域，应明确提出公共契约变更并评估对现有 Op 的影响；
- 同分确定性规则必须覆盖正负零等等值情况；
- 无效元素不能仅因填充值是 `-inf` 就被排除，必须继续使用有效范围掩码。

## 3.7 中：后端接入和缓存职责需要写准确

### 方案现状

外部后端方向正确，但缺少最小接入定义，并将缓存笼统归为后端职责。

### 代码依据

Op 层已经按设备、输入形状、输入 dtype 和构造参数缓存目标 kernel。后端 builder 返回可调用的目标实现，不需要重新实现一套相同的形状分派缓存。

### 必须修改

补充最小后端接入设计：

1. `tileops.backends` entry point 的包名和注册方式；
2. detector 的字符串和设备匹配规则；
3. kernel builder 的准确签名；
4. 输出张量分配、dtype、设备和 storage 行为；
5. 后端内部编译缓存与 Op 层目标 kernel 缓存的职责边界；
6. 首次调用、重复调用、设备切换、输入形状变化和 dtype 变化测试；
7. NPU 环境下导入公共 `tileops.attention` 的验证。

即使最终选择 Ascend C，当前公共模块导入仍会加载 TileLang 和 GPU 实现，因此导入兼容应作为第一阶段通过条件，而不是附带检查。

## 4. 测试与性能验收的补充要求

除原方案已列出的测试外，修订版必须明确覆盖：

- [ ] 同分跨阈值时重复调用的索引集合稳定；
- [ ] 不同分块或调度配置不会改变选中集合；
- [ ] `G>1` 的实际跨步布局，而不只是输出 shape 检查；
- [ ] 每行混合空窗口、短窗口、反向窗口和完整窗口；
- [ ] 尾块、重复值、全相等、正负无穷、NaN 和正负零的明确语义；
- [ ] eager 与 `torch.compile(fullgraph=True)` 的完整数值验证；
- [ ] 输出与输入无别名，输入未被修改；
- [ ] 重复调用无跨调用工作区污染；
- [ ] 完整 Prefill 和 Decode 用例的参考实现峰值内存；
- [ ] 算子自身候选区、合并区和同步区的峰值内存；
- [ ] 显存不足时的分块参考验证策略，不能通过省略完整规模验证来规避；
- [ ] 预热、设备事件计时、带宽口径、误差、中位数和 P95 等基准方法。

## 5. 修订方案必须交付的内容

方案提供者应至少提交以下五项可检查内容后再申请复审：

### A. 契约表

明确输出槽位无序、跨调用选中集合稳定、空窗口、短窗口、反向窗口、特殊值、输入 storage 行为和 compile 支持。

### B. 算法与资源表

对三个 manifest 工作负载分别列出块大小、候选数量、合并层数、片上空间、全局工作区、核划分、同步和布局。

### C. 工具链决策记录

给出 TileLang Ascend 与 Ascend C 的准确环境矩阵、最小实验、失败条件和最终路线选择依据。

### D. 正确性验收矩阵

将每项公共契约映射到具体测试，尤其补全现有验证无法发现的同分索引集合稳定性，并将 `torch.compile` 纳入最终通过条件。

### E. 性能验收公式

定义 MFU、峰值、计时范围和统计口径，同时给出延迟、有效带宽及完整工作负载的临时空间预算。

## 6. 可以保留的方案判断

修订时无需推翻以下合理判断：

- 使用独立外部后端，避免无必要地改动现有 GPU kernel；
- 不直接复制 CUDA 的线程映射、原子计数和两阶段阈值算法；
- 优先评估 TileLang，Ascend C 作为可移植性受限时的备选；
- 保持 FP32 精确选择，不默认使用 FP16/BF16 近似；
- 无效元素必须同时使用有效范围掩码，不能仅依赖 `-inf`；
- 选中索引必须为绝对 KV 索引，填充使用 `seq_len_kv`；
- 不混淆 `torch.compile` 和 CUDA Graph 支持；
- 性能测试需要区分正确性验证和预热后的设备计时。

## 7. 复审通过条件

只有同时满足以下条件，才建议进入完整实现：

1. 所有“阻塞”问题已经关闭；
2. 三个 manifest 工作负载均有可证明的资源预算；
3. 工具链路线已通过 950PR 最小实验，或有明确的实测失败记录并切换到备选路线；
4. 公共契约和验证规则不存在未决歧义；
5. MFU 与其他性能指标均可计算、可复现；
6. 最终验收明确包含 eager、重复调用、完整规模和 `torch.compile(fullgraph=True)`。
