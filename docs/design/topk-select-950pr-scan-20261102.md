# v0.1.4 桶扫描优化候选：scan-r1

2026-11-02，依据交接文档4.2.2第4项实现。当前是待 NPU 验证的候选，不发布 `topk-npu-v0.1.4` 标签，也没有新的性能结论。

## 已知差距

用户回传的新服务器 Decode 汇总来自提交 `252ad607e3a86e09f880baf785f982eca81060c2`，该提交中的内核与保存点 `49aaea36` 相同。14项契约全部通过；同轮同输入 CANN 内核9.2215μs、TileLang内核199.463μs，性能为0.0462316×CANN。完整 Prefill 尚无这轮回传结果。该数据来自用户贴出的汇总，未独立核查现场遥测或原始采样。

这与旧服务器曾出现的约3ms延迟不同；本轮不再以前次异常频率作为解释新差距的结论。性能复测仍需新一轮固定输入、环境、源码和工具。

## 本次改动

原来每轮由一个SIMT线程倒序串行遍历256桶，生成“严格更大桶的计数”，同时定位剩余配额所在桶。候选将该过程拆成独立VF阶段：

1. 16个线程各负责连续16桶，计算组内排他前缀与组总数。
2. 一个线程扫描16个组总数，得到组间偏移与全局候选数。
3. 256个逻辑桶并行合并偏移并生成最终排他前缀。仅满足 `before <= quota < through` 的非空桶写入阈值及已接受计数；这一区间唯一。
4. 下一VF阶段才更新剩余配额，避免其他线程读取变化中的配额。

新增显式UB scratch为 `(256+16)*4=1088` 字节，不代表实际编译资源总量。整数均保持int32，65536个同桶元素不经过uint16累计。阶段间使用现有 `T.SimtVF` 边界，不增加跨核同步或原子选索引。

组内与组间串行链长度分别为16；这只是减少串行算术步骤，新增VF边界可能抵消收益，不能声称已获得8倍或16倍加速。编译器是否安全降低这些阶段仍须现场确认；有unsafe ThreadSync/race警告时先停止，不以CPU验证代替设备验证。

`PARALLEL_SCAN=True` 为本候选的内核默认，host配置显式记录 `parallel_scan=True`。`PARALLEL_SCAN=False` 保留原扫描供消融对照。H仍为128，workers策略与粗筛选择保持原值，不把未经新轮验证的H256改成默认。

候选缓存、FP32完整键、NaN/±0规则、同分选较小绝对索引、K>2048溢出重扫与窗口规则保持原算法。缓存溢出与Decode跨核归并本轮未实现：前者缺少新轮占比数据，后者需要独立设计确定性归并与scratch生命周期。先隔离扫描收益，符合交接文档要求的逐项试验。

## 验证范围

新增 `tests/kernels/test_topk_select_ascend_scan.py` 可用标准Python直接运行。它提取实际kernel的串行/并行扫描AST，用CPU执行算术，并对照独立计数定义。覆盖256个单桶各65536元素、配额边界、16桶组边界、稀疏随机直方图、配额归零及反向并行迭代顺序。它不导入TileLang，不证明设备编译、SIMT同步或性能。

Windows本地只具备静态与CPU验证能力，没有NPU或可导入的torch/TileLang。新候选的14项设备契约测试、编译器资源/警告与四组性能均待操作者执行；不得把此前14项通过记到新源码上。

## 现场判定

B2Y的 `topk-950pr/SCAN_OPTIMIZATION.md` 提供完整步骤。新增同进程对照包含旧v0.1.4保存点、候选并行H128/H256及候选串行H128；保留初版与v0.1.2。每种实现同一输入、预分配输出、交替正反序50次事件采样，两轮独立重复。保存每种生成源码及哈希和历史源码引用。

先通过CPU算术检查、preflight和14项NPU契约，再看两轮H128扫描对照。事件加速比用旧H128事件中位数/新H128事件中位数，只用于扫描对照；CANN倍数仍严格使用同轮纯kernel中位数之比。没有稳定收益时停止放大，不运行完整Prefill，也不宣称优化有效。

Decode通过后才进行128行诊断及完整Prefill两组，最终需要四组同源码、50事件/50有效profile记录、同轮匹配输入的官方基线。任一规格回退仍标试验；最终默认和版本标签需结果审核后决定。
