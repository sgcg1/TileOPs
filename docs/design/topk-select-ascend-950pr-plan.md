## 2. A：契约表与确定性规则

记 B=batch，S=query 数，L=KV 长度，G=KV group，K=top_k。

| 项目 | 必须保留的行为 |
| --- | --- |
| 输入 | logits 为 FP32 `[B,S,L,G]`；starts/ends 为 int32 `[B,S]`，同设备 |
| 参数 | `0 < K <= L`；端点位于 `[0,L]` |
| 选择范围 | 每个 `(b,s,g)` 独立处理 `[starts[b,s],ends[b,s])` |
| 输出 | 新分配的连续 int32 `[B,S,G,K]`，同设备，返回 KV 绝对索引 |
| 槽位顺序 | 无序，允许两次调用槽位排列不同 |
| 确定性 | 同一输入跨调用选中相同索引集合，包括阈值同分；不能只保证分数集合相同 |
| 短窗口 | 有效位置数少于 K 时返回全部有效位置，其余填 L |
| 空与反向窗口 | `starts >= ends` 时全部填 L；反向窗口不新增报错语义 |
| 存储 | 输入不变，输出不与输入别名；有效索引唯一，重复填充值允许 |
| 编译 | eager 与 `torch.compile(fullgraph=True)` 都必须通过最终验收；不继承 CUDA Graph 支持 |
| FP32 输入域 | 不自行排除 NaN、无穷或正负零；不得将整体输入降为 FP16/BF16 |

### 2.1 确定性全序

NPU 后端拟统一使用：有效位置优先；有效位置按分数降序；等分位置按绝对索引升序。输出不必排序，但保留集合按此全序确定。数值等价的 +0 与 -0 按同分处理。不得给分数加 epsilon 打破平局，以免改变极接近 FP32 分数的先后关系。

该规则贯穿局部选择、候选合并与最终截断。局部索引先转换为绝对索引，然后参与比较。若某候选不在所属块的前 K 个，则该块已有 K 个全序更优候选，故它不可能进入全局前 K 个。由此可知逐次合并保留前 K 个与整行一次选择等价，且与块边界、核调度和合并顺序无关。

原生 TopK 若仅保证分数正确、无法指定绝对索引平局规则，则不能直接用于候选截断。必须补充阈值等分候选的确定性选择，或使用支持该比较规则的自定义排序/归并。该能力是工具链准入条件，不能靠验证匹配率接近 100% 放行。

### 2.2 特殊值：支持方向与未决验证

数值顺序拟为 `+inf > 有限数 > -inf`；NaN 的优先级按参考 `torch.topk` 降序行为核验，拟采用 NaN 优先、不同 NaN payload 视作同分并按绝对索引升序处理。NaN 规则在精确参考实验完成前保持阻塞，不能把拟定规则当作已验证事实。若 CPU/NPU 参考行为不同，记录差异并在公共 workload 层明确统一语义，不由后端单独拒绝输入。

现有自定义验证器的 assert_close 未启用 NaN 等价，不能直接声称已覆盖 NaN。修订测试时，保留普通数值精确比较，对 NaN 单独核对分类/数量和确定性索引，再比较非 NaN 数值；这属于共享语义验证的补全，不能放宽普通分数误差。无效位置通过有效性和候选数量排除，不能依赖 `-inf` 填充排除。


导入时仅注册，不编译、不分配设备工作区。初始化 torch_npu 后 detector 使用 `device.type == "npu"`；另在 builder 中检查设备为所支持的 950PR，不能把所有 NPU 都宣称为已验证支持。

```python
def build_topk_select(logits: TensorSpec, starts: TensorSpec,
                      ends: TensorSpec, *, top_k: int):
    # 接收元信息，不读取 starts/ends 的运行时内容。
    return AscendTopKSelect(...)

register_detector(target="ascend", detect=lambda device: device.type == "npu")

                        build_kernel=build_topk_select)
```

返回对象的调用签名为 `__call__(logits, starts, ends)`。分配独立连续 int32 输出，使用 logits.device，输出形状 `[B,S,G,K]`；窗口内容每次在设备上读取，不将内容或上一次结果缓存。

缓存边界：Op 已按 device、输入形状/dtype 和构造参数缓存 builder 返回的目标 kernel。后端不重复建立相同的形状分派缓存；只管理必要的已编译设备程序及其源码/编译器/架构/配置缓存键。全局工作区默认每次调用分配，不能跨流、跨设备共享可写缓冲。若以后引入池化，须有完成事件和所有权证明，不纳入首版。

测试包括首次/重复调用、输入形状变化、窗口内容变化、两个 NPU 设备的独立实例。FP32 之外的 logits dtype 应在公共校验层被拒绝，不能为测试缓存而增加非法 dtype 支持。

## 6. B：默认算法与资源闭环（拟验证基线）

### 6.1 不物化全行首轮候选

修订后 Prefill 默认使用“单行流式候选合并”，不再把 16 块的所有候选同时存放或写回全局内存：

```text
固定一个 (b,s,g)
 → 读取一个不超过 C 的窗口片段，局部保留 min(K,n) 个候选
 → 与已有不超过 K 个候选合并，仍仅保留前 K 个
 → 循环到窗口结束 → 输出
```

首个拟验证 C=4096；每次合并输入不超过 2K，三个主规格的最大值为4096，满足所查 API 长度上限，但其索引、临时空间与精确比较能力仍需实测确认。窗口总宽<=K 时直接输出有效绝对索引并填充，不调用不满足 k<=n 的 TopK。尾块使用真实 n；对齐填充不参与有效选择，合并时使用真实候选数。

### 6.2 UB 缓冲模型

每候选为 FP32 分数+int32 绝对索引，共8字节。计划采用复用的单缓冲布局，不提前承诺双缓冲：

| 区域 | 位置 | 最大容量 | 生命周期 |
| --- | --- | --- | --- |
| P | UB | 8C 字节 | 当前输入片段，G>1 时在这里完成行内 gather |
| B | UB | 16K 字节 | 两组至多 K 个候选，合并输入 |
| A | UB | 8K 字节 | 合并输出；下一轮复制到 B 的保留区 |
| 元数据预留 | UB | 1024 字节 | 端点、计数和控制量，实际编译报告核验 |
| W | UB | max(W_select,W_merge) | 两阶段顺序执行，临时区复用 |

总预算 `U_required = 8C + 24K + 1024 + W + D` 字节，D 为实际对齐、编译器隐藏分配和额外控制开销。W 必须包含确定性处理所需临时空间，不能仅计原生 TopK 的一部分。真实片上可用量 U_available 来自设备/编译报告，不能用示例的192 KiB代替。

设计上先设置128 KiB的资源预算上限，并要求设备实际可用量不少于该值；这只是分配上限，不是声称950PR恰有该容量。D和W之和必须满足下表，否则默认设计不准入。

### 6.3 三个 manifest 规格资源表

| 项目 | Prefill K=1024 | Prefill K=2048 | Decode K=2048（单核基线） |
| --- | ---: | ---: | ---: |
| B,S,L,G | 1,32768,65536,1 | 1,32768,65536,1 | 1,1,16384,1 |
| C / 全窗口分块数 | 4096 / 16 | 4096 / 16 | 4096 / 4 |
| 每块候选上限 | 1024 | 2048 | 2048 |
| 累计处理的局部候选数 | 16384/行 | 32768/行 | 8192/行 |
| 同时保留的合并输入 | 2048候选 | 4096候选 | 4096候选 |
| 顺序合并次数/依赖深度 | 15 / 15 | 15 / 15 | 3 / 3 |
| 固定UB：P+B+A+元数据 | 57 KiB | 81 KiB | 81 KiB |
| 128 KiB预算内 W+D 上限 | 71 KiB | 47 KiB | 47 KiB |
| 单行/单执行单元峰值UB | 57 KiB+W+D | 81 KiB+W+D | 81 KiB+W+D |
| 主路径候选全局工作区 | 0 | 0 | 0 |
| 输出大小 | 128 MiB | 256 MiB | 8 KiB |
| logits大小 | 8 GiB | 8 GiB | 64 KiB |

该表的“0”仅指候选不落全局内存；若编译器/API需要全局scratch，必须追加报告，不能仍报0。整算子片上同时占用上限为 active_workers×U_required，active_workers从实际核调度获取；每执行单元只处理一行，完成后复用UB，因此不乘32768行。输出不是临时工作区，单独统计。

Prefill按行号 `r=(b*S+s)*G+g` 分配给执行单元，轮转处理多行，单行合并在同一执行单元内完成，使用本地同步，不需要核间原子争抢或同步。首版不写出4/8 GiB的首轮全局候选。

### 6.4 Decode多核备选与全局工作区

仅当单核基线延迟不佳，比较4个分片并行处理4096个分数，再两层合并。各层为独立设备内核，使用同一stream的执行顺序建立依赖，不使用跨核忙等或假设隐含全局屏障。

| 阶段 | 全局输入 | 全局输出 | 候选数 | 局部资源上限 |
| --- | --- | --- | ---: | --- |
| 局部选择 | logits 64 KiB | Q0 64 KiB | 4×2048 | 按第6.2节预算，每个分片独立 |
| 合并层1 | Q0 64 KiB | Q1 32 KiB | 2×2048 | 每对输入4096，输出2048 |
| 合并层2 | Q1 32 KiB | 最终索引8 KiB | 2048 | 同一全序，最后不必写出分数 |

Q0与Q1同时存活，峰值候选工作区96 KiB，加实际全局scratch和对齐开销。最终输出另计8 KiB；各层总候选写回96 KiB，候选读取96 KiB。工作区归单次调用所有，分配在输入设备，用完由框架流语义回收。两层合并的理论依赖深度为2，代价包括3次内核启动，是否优于单核必须实测。

### 6.5 G>1布局与资源不足的处理

原始连续输入中地址为 `(((b*S+s)*L+k)*G+g)`；输出地址为 `(((b*S+s)*G+g)*K+j)`。固定g沿k读取的步长为G。G=1直接连续搬运；G>1在P中按该公式gather为一维候选，不分配完整转置Tensor。硬件若不能高效跨步搬运，则使用带边界的设备gather实现，必须测量实际读流量，不能按G=1推定性能。

若4096块的UB预算不通过，先评估C=2048：K=1024固定UB降为41 KiB，K=2048降为65 KiB，合并输入上限不变，Prefill合并次数增为31、Decode增为7。若合并临时区仍超预算，不得截断候选：停止该默认路线，提交分块排序列表的全局归并方案及完整资源表后复审。不会用“后续自动回退”掩盖未设计的内存路径。

K>2048属于公共签名允许范围但超出这套主规格基线的合并长度预算。完整适配必须另交全局有序归并/分层选择设计覆盖它，不能悄悄缩小签名域；首轮实验通过三个主规格也不等于公共输入域全部支持。该项列为完整实现准入阻塞。

### 6.6 P3前置：流式合并性能可行性检查

空间有界仅是必要条件。完整Prefill每行有16次局部选择和15次顺序合并，共31个内部阶段，32768行累计1,015,808个内部阶段；这不等于1,015,808次host内核启动。若采用C=2048，则每行32次局部选择和31次合并，共63个阶段，需要重新测量，不能只因UB更小就认为更快。

以下实验作为P1最小实验/P2评审材料，必须在P3完整实现前完成。实验内核只覆盖关闭设计问题所需的最小数据流，不等于提前实现完整公共算子；所有候选依然执行确定性全序和精确验证。

| ID | 最小实验 | 输入/控制 | 必须记录 |
| --- | --- | --- | --- |
| S01 | 单次局部选择 | C=4096、K=1024/2048；随机、全相等和阈值密集同分 | median/P95、UB、W/D、实际读写、平局处理开销 |
| S02 | 单次候选合并 | 2K→K；固定绝对索引、跨两组同分 | 同S01，另记录重排与同步开销 |
| S03 | 单行完整流式处理 | L=65536，两种K，真实31阶段 | 完整单行延迟、资源报告和生成代码；证明候选未落全局或未发生spill |
| S04 | 执行单元扩展 | 1、2、4…至可用上限；相同足量行数、相同输入 | rows/s、median/P95、实际active_workers、UB/全局scratch、同步与访存瓶颈 |
| S05 | 结构备选对照 | decode单核/4分片两层合并；prefill如有可编译的分层/全局归并备选则对照 | 同语义、同精度、同数据/设备条件的端到端延迟、物理流量、峰值工作区 |

S01/S02分别记录设备内工作和host launch成本；可使用重复执行的微基准摊薄启动开销，但不能把融合后的内部阶段当成独立host调用估算。单行粗模型 `T_row≈16*T_select+15*T_merge+T_load/store/control` 只用于解释分项，最终以S03测量为准，不将微基准相加值当作最终性能。

扩展效率定义 `E(w)=Throughput(w)/(w*Throughput(1))`，同时报告总吞吐而不只报告效率：达到带宽饱和后效率下降不自动判为设计失败。若工具不能读到真实active_workers，则标记为调度请求值，不充当实测核数。

判读规则：先排除设备共享干扰、编译差异和测量误差，再检查顺序合并/重排/确定性处理是否主导时间、增加执行单元是否提高总吞吐，以及备选是否在相同语义和资源约束下稳定更优。使用重复样本与不确定性区间说明差异；样本不足或相互重叠时标为结论不足，不凭单次最快值选择路线。不能只因阶段数多就宣布失败，也不能因没有备选就宣布可行。

若测出结构性瓶颈且无法用局部调整解决，应在P3前变更默认结构并重交资源表和证据。P2须形成明确的“保留流式基线/调整结构/证据不足暂停”决策。此检查只筛查性能路线风险，最终性能评价仅采用第9节的CANN TopKV2延迟对比和加速比。UB、核数、流水及搬运数据仅用于资源核验和定位瓶颈，不作为独立性能评分或达标指标。

## 8. 完整规模参考验证与内存预算

两个prefill的logits各8 GiB，端点合计256 KiB，输出分别128/256 MiB。整行TopK参考中的mask、masked副本、int64索引和框架临时空间可能显著扩大峰值，必须单独测量，不能只报输入大小。

计划按64个query一批进行参考验证：G=1、L=65536时，每批FP32分数16 MiB，bool有效掩码约4 MiB，masked副本16 MiB，K=2048的int64参考索引1 MiB；至少约37 MiB的显式新增量，再加库临时空间、验证gather与排序结果。原始完整输入和待验证输出继续存在。批大小根据实测峰值可下调，但必须遍历全部32768行和所有group，不采样替代完整规模正确性。

若NPU上的参考算子不支持或内存不足，按行批次复制到CPU，采用已确认语义的CPU参考完成全量验证；输入生成、参考和误差策略仍归workloads层。传输与参考时间不计入被测内核时间，验证结果附带实际执行行数和峰值内存。完整规模连输入和输出都不能分配时，报告未验证/资源不足，不报通过。

## 9. E：CANN TopKV2延迟与加速比

本节取代此前MFU、比较吞吐利用率及理论峰值达成率的验收口径。性能评价仅保留延迟与相对CANN TopKV2的加速比。资源容量仍是正确执行的约束；Vector活跃占比、带宽、吞吐量和扩展效率如需采集，仅用于内部诊断，不作为额外性能评价或95%目标。

### 9.1 基线身份与输入

基线固定为CANN TopKV2。记录实际调用接口、CANN/OPP组件版本、执行kernel名称、参数、workspace大小及可追溯源码/二进制身份。不得只因某调用名为torch.topk便认定它执行了目标TopKV2；若使用torch_npu封装，须通过调用链或profiler确认。

优先覆盖三个manifest完整窗口、G=1的FP32规格，使用同一950PR设备、相同输入数据、K、窗口和布局。G=1时可以将输入视为[B*S,L]。两种实现均须先通过相同正确性验证；有差异的特殊值或窗口用例不能直接发布等价加速比。

### 9.2 计时边界

主对比采用满足公共输出契约的端到端设备链延迟：从公共输入准备完毕开始，到int32、连续、绝对索引输出准备完毕结束。计入各实现必要的选择/合并、窗口处理、布局重排、索引转换和填充，不计编译、输入生成、参考验证和主机到设备初始传输。基线额外产生values等成本不隐藏，明确所用API是否支持仅索引输出。

若另报纯TopKV2内核与我们的纯选择内核延迟，独立标为kernel-only，不与端到端结果交叉计算加速比。公共Op同步完成的墙钟延迟可单列，但两侧必须同口径包含分派、检查、分配、调度和完成等待，不能用异步提交时间冒充执行时间。

主规格采用预先连续输入。非连续公共输入另测时，连续化复制计入两侧端到端成本和峰值内存；后端连续输入假设由Op._run_on_target的contiguous保证，不能在计时前偷偷完成复制而仍标为非连续端到端结果。

### 9.3 统计与公式

先完成正确性验证和编译，再预热至少20次；每规格至少100个稳态样本，重复3轮，报告median与P95延迟。设备事件在同一stream记录整个设备链；小decode可批量重复摊薄事件开销，但明确批大小，不将批均值标为单次P95。共享设备有干扰时标明，不采用单次最快值宣称改进。

对每个规格和相同计时口径分别计算：

`Speedup = median(T_CANN_TopKV2) / median(T_ours)`

- Speedup > 1：我们的实现更快。
- Speedup = 1：耗时相当，结合测量波动判断。
- Speedup < 1：CANN基线更快。

不使用三规格平均值掩盖单项结果。用户尚未指定最低加速比，因此报告实测结果，不擅自设置“必须超过CANN”或其他数值达标线。P95也分别列出两侧延迟，不将median比值解释成P95加速比。

报告表：规格、设备链/公共调用口径、CANN median/P95、我们的median/P95、median加速比、正确性状态、测量轮次与干扰说明。资源报告保留为可运行性证据，MFU定义不再阻塞P3；其他准入阻塞仍须逐项验证。
