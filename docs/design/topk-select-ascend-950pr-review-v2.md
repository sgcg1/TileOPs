## 3. 新增技术论证的复核结果

### 3.1 确定性全序与流式合并在数学上成立

修订版采用以下拟验证顺序：

1. 有效位置优先；
2. 分数降序；
3. 等分位置按绝对索引升序；
4. NaN 的优先级和 payload 规则待参考实验确认后再纳入同一全序。

在 NaN 规则最终闭合后，该比较关系可以为不同绝对索引建立确定性全序。逐块保留前 K 个、逐次合并仍保留前 K 个的证明成立：未进入所属块前 K 个的候选，已经至少有 K 个全序更优候选，因此不可能进入全局前 K 个。

对于 K≤2048 的默认基线：

- 每个局部块最多产生 K 个候选；
- 已有累计候选最多为 K 个；
- 每次合并输入最多为 `2K`；
- `2K <= 4096`，满足所查 Normal TopK 的长度上限；
- 窗口总宽不超过 K 时直接返回全部有效位置，不调用不满足 `k <= n` 的 TopK；
- 尾块和对齐填充通过真实候选数及有效性排除，不依赖 `-inf` 作为唯一无效标记。

上述结论依赖确定性全序在局部选择、阈值同分处理和合并阶段均被真正实现，不能只依赖原生 TopK 的分数输出或接近 100% 的匹配率。

### 3.2 UB 资源表算术正确

修订版定义：

`U_required = 8C + 24K + 1024 + W + D`

其中 P、B、A 和元数据的固定部分计算如下：

| 参数组合 | 固定 UB 计算 | 结果 |
| --- | --- | ---: |
| C=4096，K=1024 | `8×4096 + 24×1024 + 1024` | 57 KiB |
| C=4096，K=2048 | `8×4096 + 24×2048 + 1024` | 81 KiB |
| C=2048，K=1024 | `8×2048 + 24×1024 + 1024` | 41 KiB |
| C=2048，K=2048 | `8×2048 + 24×2048 + 1024` | 65 KiB |

相应 128 KiB 设计预算下，C=4096 时留给 W+D 的上限分别为 71 KiB 和 47 KiB，表内数值正确。

这些结果只证明固定缓冲模型自洽，并不证明真实实现已经满足资源约束。仍须由安装版本 API、Tiling 和编译报告补齐：

- 原生 TopK 的源索引、目的值、目的索引和 k_pad 对齐空间；
- 确定性同分处理所需空间；
- 编译器隐藏分配及额外控制开销；
- 950PR 实际可用 UB；
- 任何额外全局 scratch。

### 3.3 Decode 多核工作区计算正确

Decode 备选方案中：

- Q0：4×2048 个候选，64 KiB；
- Q1：2×2048 个候选，32 KiB；
- 最终输出：2048 个 int32 索引，8 KiB；
- Q0 与 Q1 同时存活，候选工作区峰值为 96 KiB；
- 不计最终输出的候选写回为 64+32=96 KiB；
- 合并阶段候选读取为 64+32=96 KiB。

使用同一 stream 的内核顺序建立层间依赖，不假设跨核隐含全局屏障，该设计方向正确。

### 3.4 性能语义流量计算正确

修订版采用：

- `N_eff = G * sum_bs(max(0, ends-starts))`；
- `Bytes_sem = 4*N_eff + 8*B*S + 4*B*S*G*K`。

三个全窗口规格的结果已复核：

| 工作负载 | Bytes_sem |
| --- | ---: |
| Prefill K=1024 | 8,724,414,464 byte |
| Prefill K=2048 | 8,858,632,192 byte |
| Decode K=2048 | 73,736 byte |

这些数值与仓库现有 roofline 语义一致。方案同时区分语义最小流量和实际物理流量，口径合理。

### 3.5 连续输入假设有 Op 层保证

外部 target 路径会绕过 `TopKSelectFwdOp.forward()`，但 `Op._run_on_target` 会统一对非写入输入执行 `.contiguous()`。因此，后端按连续输入设计地址映射本身不构成缺陷。

若性能报告包含非连续公共输入，则连续化复制应计入公共 Op 的资源或墙钟成本；主规格基准仍应明确输入是否预先连续。

### 3.6 CallSpec 公共导入阻塞属实

本地 `src/tileops/_kernels/call_spec.py` 确实从模块自身导入 `CallSpec`，但文件中没有该类定义。该问题会影响公共模块导入，修订版将其列为 P0 是合理的。

修复时必须恢复可追溯的正确源码或基础类定义，不得：

- 猜测伪造一个 CallSpec；
- 修改无关内核绕过导入；
- 将问题错误归因于 NPU 硬件或 Conda 依赖。

### 3.7 NaN 验证器判断正确

现有 workload 调用 `torch.testing.assert_close` 时未传 `equal_nan=True`。PyTorch 默认 `equal_nan=False`，因此修订版认为当前验证不能直接证明 NaN 语义正确，判断成立。

后续特殊值验证应保留普通数值的 `rtol=atol=0`，并单独核对 NaN 分类、数量和确定性索引，不能通过放宽容差或仅比较匹配率放行。

## 4. 建议补充：流式合并的性能可行性 sanity check

该项不是新的正确性阻塞，但应在 P3 完整实现前关闭性能路线风险。

默认流式算法对每个完整 Prefill 行执行：

- 16 次局部选择；
- 15 次顺序合并；
- 合计 31 个内部选择/合并阶段。

32768 行合计为 1,015,808 个内部阶段。它们不是同数量的 host kernel launch，但仍可能引入显著的指令、同步、局部数据重排和确定性后处理开销。当前资源表证明了空间有界，尚未证明该结构具有合理的吞吐扩展性。

建议在方案第 6 节或 P2 交付物中补充以下最小实验：

| 实验 | 必须记录的结果 |
| --- | --- |
| 单次局部 TopK | C=4096、目标 K 下的延迟、UB、临时空间和确定性处理成本 |
| 单次候选合并 | `2K→K` 的延迟、UB、读写量和同分处理成本 |
| 单行流式处理 | 31 阶段的完整单行延迟及中间候选不落全局的证明 |
| 执行单元扩展 | 不同 active_workers 下的吞吐量、资源占用和扩展效率 |
| 备选结构对比 | 与 Decode 多核方案、全局归并或其他分层方案的同口径比较 |

若单行流式结构的吞吐明显不具备扩展性，应在完整实现前调整默认路线，而不是等到 P4 才发现结构性性能问题。
