# TopK后续优化路线复评：以首轮全窗处理为主线

结论：第4.2节应从“溢出治理→行拆分→尾部利用率→串行桶扫描”的历史排序，改为“首轮计算/搬运效率→分片计数与压缩→Decode首轮分核”，同时独立收集Prefill阶段证据。缓存溢出、尾部调度和扫描不再同时占据最高优先级。

本文件是性能方法分析，没有新增NPU结果、性能承诺或默认配置变更。生产kernel仍为SHA 987da9f9d314f8744bef05a628e60a14b88e63db320374f36a3b6411ce5eb2e3；当前stage1工具只支持该源码，后续候选不能绕过其身份/阶段布局检查。

## 证据及适用范围

直接证据来自[本轮阶段档案](https://gitcode.com/JotaroSSR/B2Y/blob/main/experiments/topk/20261102-stage1-decode-163258/analysis.md)：Decode R1/N16384/K2048/W1/H128，FP16粗筛+精确FP32后续选择。50轮1350个区间与原始时间戳已复核，候选轨迹16384→835→835→25→0，无缓存溢出。首轮histogram 55.983μs、compact 73.2385μs；两段同次合计中位数129.2055μs，占已测区间同次总和的中位比例81.039%。

五轮scan合计7.345μs；quota归零后的最后一轮1.983μs、最终tie/收尾9.589μs。生产事件162.7365μs，完整插桩168.6810μs，增加3.65%。这是优化优先级证据，不是无插桩阶段成本精确分摊，也不能直接推广到Prefill或与CANN纯kernel延迟混算倍数。

原第4.2节与交接时的ops-math缓存源码一起复核：快照提交e287c428bf5bcdb8279b0e4764f4b7914ec66003，5份相关源文件Git blob SHA均与source-index一致。它是当时的源码参考，不能据此确认当前服务器CANN9.3实际使用了哪条内部路由。

## 一、第4.2节必须修正的前提

| 历史判断 | 当前修正 | 对决策的影响 |
| --- | --- | --- |
| 逐轮收窄、UB复用是待迁移能力 | 已实现，本轮已把16384缩至835，再到25 | 重点转为让首轮更便宜，不重复实现已有机制 |
| 首要治理2048缓存溢出 | 本次Decode没有溢出，Prefill尚无阶段轨迹 | Decode降级；Prefill先测溢出率、分位数和重扫时间 |
| 串行256桶扫描仍是当前主要实现 | 默认已是grouped scan，串行仅为消融路径 | 保留已验证实现；原“换二分”理由已过时。二分本身还需要累计计数，不能直接替代构造前缀 |
| Prefill尾部8/56利用率很差，因此收益可能很大 | R32768/W56时最多每worker586行；等成本理想均衡585.1429行，整体时间只约省0.1463% | 不为这一个尾部先引入复杂行拆分；不排除其他小R或行耗时不均衡场景 |
| 任何atomic抢位都违反确定性 | 契约是选中集合确定，输出槽位无序。禁止用抢位决定阈值同分者保留谁；已确定全部入选的元素可以原子分配输出槽位 | compact可以分片、批量预留，不必为无序输出强加全局排序 |
| 主规格K/N均约1.5%～3% | Prefill分别1.5625%/3.125%；Decode为12.5%，有效窗口又可能不同 | 不能只用一个比例选算法，更不能把CANN的分档阈值当通用最优定理 |
| K>2000意味着必须采用64位value+index排序 | 缓存CANN代码中还受IS_SORT及模板条件控制；我们的输出不要求排序 | 64位打包可作独立比较/排序设计，不是当前必需改动 |
| AB候选必须源码SHA一致 | 不同实现当然会有不同SHA；应各自冻结并记录，保证同一实现的重复测量身份一致，输入一致 | 避免把“源码身份可追溯”误写成禁止代码变化 |

还有一处逻辑缺口：“只重扫边界桶元素”必须有可寻址的候选索引/键列表、连续化缓冲或等价元数据。只给原全窗循环加前缀判断，仍要定位并读取输入，不能凭逻辑过滤宣称I/O变成O(边界桶大小)。

## 二、重新排序的路线

| 顺序 | 方案 | 针对的实测问题 | 成本与主要限制 |
| --- | --- | --- | --- |
| A0 | 首轮专门化、粗键只计算一次 | 首轮两段保留动态round分支及重复展开的粗键表达式 | 改动较小；Bisheng可能已消除重复，收益待测；避免再增加过深静态嵌套 |
| A1 | 缓存首轮coarse byte，复用到compact | 两段重复读全窗并计算粗键 | Decode额外16KiB/worker；首轮多写UB，可能抵消收益，先单独对照 |
| A2 | 分片histogram，随后复用分片计数给compact分配区间 | histogram潜在热点争用、compact全局游标 | 从4片做起；4片256桶int32数组4KiB，新增归并/初始化与VF边界 |
| B | Decode仅首轮跨核，后续小候选保持单核 | 约80%的包络时间仍由一个worker遍历全窗 | 高潜力、高实现成本；跨核工作区、全局阶段同步、额外launch可能吃掉收益 |
| C | quota归零后的条件跳过 | 末轮和tie/收尾有可见空转 | 中等收益预算；历史guard试验未确认整体收益，必须重新隔离验证 |
| D | Prefill专属溢出/调度治理 | 尚无对应阶段证据 | 补证据后决定，不从Decode类推；K1024当前甚至不走FP16粗筛 |
| 暂缓 | 再换扫描算法、单个大Prefill尾部优化、无证据扩大缓存 | 目标占比小或本次未发生 | 保留为后备，减少同时改动变量 |

A1和A2是竞争/可组合的候选，不要求先把所有方案叠加。先确认单项有效，再只组合通过的方案。保持已验证H128；H256 grouped scan已有现场失败记录，不能把增加线程当作无条件优化。B的收益/launch成本可以尽早做小验证，不必等单核路线全部尝试完。

### A0/A1：让第一次看输入的结果可以复用

生成C++在两个全窗VF里重复展开coarse_byte转换与条件，并在运行时判断round。可以给粗筛单独的首轮路径、保留统一的精确FP32后续路径，并显式物化一次粗键。必须保持原round到byte_shift和缓存乒乓奇偶的对应关系，不能拆出首轮后直接重置编号。C++重复表达式不证明最终指令重复，应同时看生成/最终代码和无插桩延迟，不能预告收益。

更有辨识度的候选是**仅缓存1字节uint8粗键**：histogram读取原FP32并写coarse_cache[i]；得到全局粗阈值后，compact扫描UB粗键，严格大于阈值者只需写索引，等于阈值的835条才需要读取原FP32、生成完整键并写候选缓存。索引由i隐式给出，不再为全窗保存一份int32索引。

本次粗键缓存大小为16384字节=16KiB，原compact对全窗16384个FP32的逻辑读取可缩为边界835条的读取；这是算法访问量，不是DRAM事务测量。首轮增加UB写入，compact仍有UB读与原子/散写。边界桶很大时，第二次FP32读取并不会显著减少，反而多付缓存成本；全同分等分布也要评估。它与历史完整FP32行缓存的成本不同，但历史回退足以说明“加缓存就快”不成立。

N65536时缓存变64KiB，不能自动推广；需核对实际UB、对齐、寄存器、调度和总体资源。K1024 Prefill当前COARSE=false，应保留原路径。粗键只能过滤，最终胜负仍用原FP32完整键；NaN、±0、FP16上下溢/舍入边界必须保持现有语义。窗口无效位置不能读取未初始化粗键。

直方图完成之前，全局阈值未知，因此不能简单把histogram和最终compact融成“看一遍就决定丢弃”。减少重算/重载必须付出缓存或候选物化等成本。

### A2：先分片计数，再利用计数给压缩分配地址

先把256桶拆成S组私有计数银行，例如按逻辑lane对S取模，不假定CUDA warp宽度。各bank用int32累计，独立VF精确合并为原全局256桶，再走现有grouped scan。S=4数组4KiB，S=8为8KiB；这些是bank自身大小，是否复用原hist存储及额外scratch另行计算。原子次数未减少，只是分散潜在冲突，收益是假设；布局、对齐和bank冲突也要核查，不能由逻辑分片数推断线性扩展。

第二个独立试验可复用这些分片计数：对每个桶计算全局桶偏移加“此前分片计数”的前缀，给每个分片不重叠的输出区间；边界桶另用分片前缀分配候选区间。分片内仍可保留原子游标，减少对一个全局计数器的争用，避免为了消除所有原子而引入昂贵的逐元素全局scan。

histogram与compact必须使用相同元素归属规则；生产计数、归并、初始化游标和消费必须有明确VF依赖边界。边界候选总数由全片合计得到，超过2048仍要完整计数并走既有精确退化路径，不得只对截断缓存继续选择。同分截断仍由FP32阈值与绝对索引规则决定。

本次首轮compact约1767次已接受输出预留+835次候选预留，共2602次逐元素原子。若进一步尝试每128元素做两类掩码/prefix并批量预留，理论上预留次数可降至每类每块一次、最多256次；但这是指令计数模型，新增prefix、掩码、scatter和同步可能更贵。鉴于历史SIMD直方图回退与warp原语降低失败，这一步必须先做小能力验证，不能照搬CUDA代码。

主仓文档明确区分SIMT/SIMD，也明确自动调度不代表任意T.Parallel会自动变成SIMD指令；此处只据此选择验证方向，不推定现场0176构建已经支持需要的全部原语。[TileLang主仓说明](https://github.com/tile-ai/tilelang/blob/main/tilelang/ascend/README.md)

### B：Decode先分首轮，避免“每核local TopK再大归并”

建议先比较P=2/4/8个worker做首轮，而非直接用满56核：

1. 各worker处理互不重叠的连续输入块，生成私有coarse histogram。
2. 归并P份计数得到全局阈值，并从各分片计数计算已接受数/边界数的全局偏移。
3. 各worker并行压缩，写全部已确定入选的索引和边界桶完整候选列表。
4. 由单worker读取设备元数据，边界≤2048时将候选装入UB继续精确FP32收窄；溢出先走已验证回退，之后再研究GM候选溢出治理。需要重建quota、粗前缀和已提交输出数，不假定跨kernel保留UB，也不为分支额外做每次调用的D2H同步。

这样优先并行本轮129.2μs的大工作域，并保留835条之后已经有效的单核收窄。跨核共享256桶原子不是首选：先用私有计数+归并保证独立性和可核对性。第一版可在同一流中用分阶段kernel保证全局依赖顺序，先量化额外launch/工作区/GM通信；不直接引入无法验证驻留条件的同kernel全局自旋同步。

简单的P份local TopK候选上界是min(P×K,N)：本次P2/4/8对应4096/8192/16384条；P=8时每块仅2048条，local TopK会保留整块，失去剪枝。全局直方图阈值路线更贴合已观测到的835条边界，但实现复杂度也更高，尚未证明更快。

多kernel方案必须评估完整调用事件与设备阶段包络，不能只把各kernel时间相加就冒充流水墙钟，更不能继续沿用只解析一条main kernel的旧性能倍数脚本。Probe2约14μs事件包含整个调用，不可直接当成单次launch成本。

仅作预算：用counter包络T=161.7985μs、首轮H=129.2055μs，若其余成本固定、H加速2/4倍，模型总时间约97.196/64.894μs，整体约1.665/2.493倍。分核还需加L(P)等通信/同步成本，基本盈亏条件是L(P)<H×(1−1/P)；这是筛选试验的模型，不是延迟预测。

### C/D：次级改动与Prefill补证据

quota归零后可研究跳过剩余radix轮和tie工作，但须覆盖所有结束位置，不得无条件删tie。第1轮本次accepted=0却细化了FP32前缀，不能把“无输出”误认为“无用轮次”。历史v0.1.1的guard并未建立整体收益，新的实现仍要重新验证编译嵌套、控制流和Prefill回退；不把9.589+1.983μs直接承诺为生产可省时间。

Prefill需分别调查N65536/K1024的直接FP32路径和K2048粗筛路径：代表性行的各轮候选分布、>2048比例、重扫时间占比、行间耗时差异。先用小规模固定行定位，再完整测量；当前单worker stage1不能直接修改参数扩展到多worker，记录槽位与归属需重新设计。

确有溢出时，优先比较有限GM候选列表/子分桶与原全窗过滤。GM列表必须有容量与完整计数策略，预算包括读写通信和地址索引；可研究按worker复用工作区，避免按所有R×N无界分配。64位打包/排序只作有证据的备选，其比较顺序还必须包含有效性、规范化FP32键和较小索引优先。

行拆分只在行数少、核闲置时有理由。大Prefill已按行并行占用核，给每行更多核会减少同时处理的行数，不能期待同样收益。尾部优化也要用总调用时间和行耗时分布评估。

## 三、最小实验顺序与接受条件

建议不做全组合搜索：冻结baseline，先A0；单独试A1；A2先4片hist，再在其上独立比较分片compact；仅组合已稳定获益的项。同时以小P评估B的额外launch/归并成本，决定是否值得继续。C作为独立小补丁，D依据Prefill新证据进入。

每项先做CPU语义/资源与生成代码检查、小规格设备正确性和同进程固定输入AB/BA，快速淘汰失败或无收益候选；有希望的候选再完成14项完整契约、独立进程重复、128行与完整Prefill回归。未过完整检查的候选明确标为试验，不进入默认。有资源或编译警告先解决。NaN/Inf/±0、FP16边界、全同分、K>2048、缓存溢出、窗口与非连续输入继续保留。

性能判断以无插桩端到端事件及正确口径的内核/流水设备记录为主；阶段计时用于解释。至少保留独立进程重复、逐次样本、各实现源码/二进制身份、输入hash和负载记录，避免只报最小值；扩展随机种子、分数/粗桶分布和有效窗口，防止只针对一个固定输入过拟合。不同实现允许SHA不同，同一实现的身份在对照和重复间必须固定。

若通用默认导致任一主规格回退，则不作为通用默认；有明确守卫的Decode专用路由可单独评估，必须证实未被路由的原路径保持原实现和正确性。后续优化仍通过个人fork同步，操作命令先写B2Y，结果直接放AAA_Results，不要求用户制作校验文件。
