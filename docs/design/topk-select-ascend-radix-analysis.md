# TopKSelectFwdOp：GPU Radix算法分析与950PR实现方案

日期：2026-10-29。性质：基于当前本地源码的静态分析与待验证设计；本轮没有修改内核或开展服务器实验。本文不是新的完整实现准入结论。

## 1. 结论与研究范围

当前GPU内核使用分级Radix选择：先以FP16有序编码的高8位做256桶粗筛，再对阈值桶内的FP32有序键逐字节细化。它不对整行排序，也不做4096分块TopK后逐块合并。

950PR主研究路线应保留“直方图→后缀计数→阈值桶→接受更高桶→细化边界桶”的结构，使用SIMT、UB原子计数、有限候选缓存及溢出重扫。此前bitonic选择/合并实验是不同算法的对照，不能替代这条路线的性能证据；不据其结果继续默认推进bitonic完整单行实现。

分析对象为当前文件 `src/tileops/_kernels/attention/topk_select.py`，而非未知上游版本。源码注释中的GPU性能数字是原作者记录，本轮未在GPU上复测。

## 2. GPU实现逐段说明

### 2.1 一行的含义与并行粒度

源码第109行：一个CUDA block负责一个 `(b,s,g)`。输入沿KV轴读取 `[starts[b,s], ends[b,s])`，输出为 `[b,s,g,:]` 中的K个KV绝对索引。不同query、batch、group之间没有共同TopK。

默认1024线程；每线程先装入8个FP32值，再计桶，使一组循环覆盖8192个KV位置。只加载与窗口相交的8192元素块，边界块可能读入窗口外的有效张量位置，但只有窗口内元素参与计数。输出先全部写L，作为未选中槽位的填充值。

`annotate_min_blocks_per_sm(2)`、32寄存器附近的占用率约束、共享内存缓存大小及GPU特定partial barrier都属于GPU调优，不能照搬为NPU参数。

### 2.2 第一层：256桶粗筛

第72—76行对分数进行以下操作：

1. 转换为FP16，取得16位表示。
2. 负数取反；非负数设置最高位，使正常数值的编码随分数增加。
3. 右移8位，得到0—255的桶编号。

因此不是简单“只看指数”：保留的是变换后FP16的高8位，其中包含符号、指数和部分尾数信息。

FP16在这里仅用于确定粗桶。靠近第K名、被粗分桶混在一起的候选，后续仍按原FP32的完整32位键比较。对有序的普通数值，粗分桶把不同分数合并，不应颠倒先后；所以这不是以FP16近似分数直接决定最终TopK。

同一block中的线程向共享内存256桶直方图执行原子加。对绝对索引小于BIN_CACHE的位置，将桶编号按每元素1字节缓存，后面的收集遍历优先读缓存。

### 2.3 后缀计数与阈值桶

源码把直方图改为后缀和：

`H[b] = 桶编号大于等于b的候选数`，`H[256]=0`。

用8轮倍增完成256项后缀扫描。设本轮还需r个元素，源码寻找：

`H[t] > r 且 H[t+1] <= r`。

于是桶号大于t的 `A=H[t+1]` 个元素可以全部选入，剩余需求变为 `r-A`，只需在桶t中继续细化。严格不等号是源码的实际条件，不能擅自换成另一种边界定义而不同时调整收集逻辑。

当本轮候选数不超过r时，阈值保持-1，全部候选可直接选入。GPU通过该哨兵及预填L处理短窗口；NPU可以将该情况做成显式提前返回。

例：需要5个，某阈值桶上方已有3个，阈值桶内有7个。上方3个直接进入输出，后续问题变成“只在这7个里选2个”。无需排序其余数据。

### 2.4 收集与输出

第215行起第二次遍历窗口：

- 桶号高于阈值：直接把索引写入最终输出。
- 恰在阈值桶：保留原FP32有序键及绝对索引，等待下一层筛选。
- 更低的桶：丢弃。

`atomic_add(..., return_prev=True)`返回旧计数，用作唯一写入位置。后缀计数在收集时也被复用为各桶的输出游标；这种复用有严格的生命周期与同步要求。

### 2.5 第二层：最多4轮FP32字节细化

`convert_to_uint32`生成正常数值的FP32有序编码。第248行起依次处理位段：

`31:24 → 23:16 → 15:8 → 7:0`。

每轮仍是256桶直方图、后缀和和阈值选择。高桶候选进入最终输出，边界桶交给下一轮；已经确定的高位前缀被记录在`s_refine`中，重扫时用于过滤。

这相当于沿第K名所在的桶不断向下追踪，而不是给所有桶继续排序。粗筛后最多还有4轮精确细化；某轮需求归零就提前结束。

### 2.6 2048是缓存容量，不是K上限

候选使用两套容量2048的共享内存缓冲交替存放，每条记录为4字节索引＋4字节键，总共32KiB。

候选总数始终完整计数。若超过2048，仅缓存前2048条，但下一轮`rescan=True`，重新遍历原窗口，并按粗桶及已确定的键前缀找出所有候选；不会只在截断缓存中继续选择。

这点是正确性机制，不是可以省略的性能优化。源码测试`test_topk_select_threshold_bucket_past_staging`专门构造8192个分数挤在一个粗桶的情况。`test_topk_select_window_past_the_bin_cache`则覆盖窗口越过桶缓存的情况。

### 2.7 最后一轮与语义限制

4个字节均相同时，最后一轮通过原子抢位并限制输出位置小于K，选出所需数量的同键候选。原子返回值保证写入地址唯一，不保证较小绝对索引优先；静态源码不能证明阈值同分时选中集合跨调用固定。

NaN进入FP16转换及位编码时，其符号/payload未被统一为一个等价类，不能将当前GPU代码描述为已经实现“所有NaN同分且按索引升序”。本轮没有证明GPU在所有NaN输入上的数值选择正确性，也没有实测其同分不确定性。

950PR实现需要遵守已经统一的特殊值与确定性规则，不能复制这些未保证的细节。

## 3. 950PR同算法实现

### 3.1 执行与工具路线

先做单线程块负责一行的SIMT版本；行号展开B*S*G，按原布局计算GM地址。块内用UB共享直方图、缓存和计数，通过显式同步建立阶段依赖。线程数先作为128/256等待测参数，不继承GPU1024线程配置，也不把launch块数当成实测活跃核数。

官方`asc_atomic_add`文档明确950PR支持int32/uint32的UB原子加并返回旧值；官方Histogram优化样例使用UB直方图及`asc_syncthreads()`。这给出了实现所需的底层能力依据，不等于当前TileLang版本的对应lowering已经通过测试。

沿用已隔离的TileLang Ascend实验环境，首先验证UB原子加、取旧值、线程块同步、FP16位重解释和后缀扫描。如果语言层无法正确表达，保留失败证据，以Ascend C SIMT最小原型验证同一算法原语；不伪装成已解决正式依赖/编译后端问题，也不静默安装另一个同名工具链。

### 3.2 统一全序与粗桶

FP32精确键使用已验证方向：NaN统一为最高键，±0统一，其余按符号位进行单调变换。同键按绝对索引升序。

主方案保留GPU的FP16粗桶：先按原FP32整数位判断NaN/符号/零；NaN固定为粗桶255，不依赖浮点`x!=x`；其余做单调FP16转换和位变换。必须验证非NaN值的粗桶随精确键非递减，特别检查FP16舍入边界、溢出、下溢、±0与±inf。

FP16转换只参与粗筛，精确选择始终使用FP32完整键。若所选转换或lowering不能满足粗桶单调性，粗筛不能准入。直接对规范FP32键按高字节开始做4轮Radix可作为正确性对照；它与GPU粗桶的分布不同，其性能不能混为一谈。

### 3.3 每行流程

```text
读取start/end，输出预填L
  空/反向窗口：结束
  窗口宽<=K：输出全部有效绝对索引，结束
  256桶粗筛：直方图→后缀和→确定阈值
  接受高桶，收集阈值候选（键＋索引），保留完整候选数量
  对精确键的4个字节逐层细化
    缓存容得下：读取UB候选
    容不下：重扫GM窗口，用粗桶与已定前缀过滤
    每轮接收高桶，更新输出数量、剩余需求、阈值前缀
    剩余需求为0：结束
  精确键仍同分：按绝对索引顺序选足剩余数量
```

多份子直方图可以分散UB原子热点，最后在块内汇总。初始先验证单直方图，再比较4份等配置；对全相等与密集同分数据单独测量，不能只报告随机输入。计数原子无需返回值，候选入缓存的游标原子需要返回值，两者不必强制生成相同指令。

后缀扫描可先使用全部线程都参与的同步及双缓冲256桶实现；不能直接移植CUDA的256线程partial barrier。所有barrier必须在块内一致控制流上执行。异步搬运还需相应完成事件，不以UB原子操作代替同步。

### 3.4 确定性同分决议

仅当最终精确阈值键的候选数量超过剩余需求时，重新按KV绝对位置从小到大遍历原窗口，查找等于该精确键的元素。

每个输入tile计算等键掩码和exclusive prefix sum；用此前tile累计数量决定写入位置，只写最前面的r个等键索引。tile按索引递增顺序处理；tile内部前缀给出确定顺序。可以采用“连续分段的线程局部计数→线程计数前缀→段内前缀”的实现，不要求复制一个未经验证的GPUwarp原语。

即使之前候选缓存由原子加压紧、其槽位顺序不固定，该最终重扫仍选中同一组最小索引。较高桶内元素是全部接受的，槽位顺序可变而集合不变，因此无需把整个输出排序。

### 3.5 任意K与G

候选缓存M固定2048，与K分离。K>2048仍直接把已接受候选写入最终GM输出，只有阈值桶需要细化；其大小超过M就重扫。这一路线不需要在UB中合并2K条记录，也不需要将K>2048另交给全局排序。

这是一项算法支持设计，尚非完整合法输入域运行通过；需实测K=2049、4097、K=L、短/空/反向窗口及阈值桶溢出等边界。

G>1按 `(((b*S+s)*L+i)*G+g)` 读分数，不物化全张量转置。非连续公共输入仍由Op连续化，其成本在正式设备链比较中计入。

## 4. 有界UB预算（拟定值，非实测报告）

先取候选缓存M=2048，搬运/前缀tile C=2048，桶缓存BIN_CACHE=32768；单缓冲搬运，不预设双缓冲。

| 项目 | 预留字节 |
|---|---:|
| 两套候选键＋索引 | 32768 |
| 每元素1字节粗桶缓存 | 32768 |
| 4份256桶uint32子直方图 | 4096 |
| 两份257项后缀/扫描计数 | 2056 |
| C个FP32输入 | 8192 |
| C个FP16转换临时值（保守预留） | 4096 |
| C个uint32掩码 | 8192 |
| C个uint32压紧/同分前缀 | 8192 |
| 控制信息预留 | 1024 |
| 合计固定部分 | **101384，约99.008KiB** |

仍沿用128KiB设计预算时，D及未列开销只剩29688字节，约28.992KiB；必须由实际编译报告关闭。若将粗桶缓存增到65536，上述固定部分约131.008KiB，已经超预算，不能直接照搬GPU64KiB缓存。

GPU当前共享内存静态数组合计为：64KiB桶缓存时99352字节，约97.023KiB；32KiB缓存时66584字节，约65.023KiB。GPU线程寄存器数组不在该共享内存统计内。不能用这个数字代替NPU预算。

第一版可关闭粗桶缓存来简化验证、降低UB占用，然后测量32KiB缓存的收益。缓存之外的元素重读原分数，不能因缓存未覆盖而丢弃。若预算仍不闭合，降低tile/子直方图数量并重交实测资源，不提高预算来掩盖D。

单行主路径不设计显式全局候选scratch，候选溢出走重扫；最终K个索引是输出，不是scratch。编译器隐藏分配、spill和runtime实际工作区必须单独核验，尚不声明实际scratch为0。

## 5. Prefill与Decode

Prefill有32768行，先按行独立分配线程块；不在同一行上引入跨核忙等。记录请求块数及真实活跃执行单元，评估UB、寄存器和调度对并发的影响。

Decode先用同一单行算法。若单块不能达到合理延迟，再研究同算法的分片直方图→全局汇总阈值→分片细化；每一层用独立kernel和同stream顺序建立依赖，单独预算全局计数与候选空间并计入launch成本。它不是此前的四块排序后归并方案，不作为首版已证实优化。

## 6. 验证顺序与准入

1. 原语探针：950PR UB原子计数/旧值返回、同步、256桶后缀和、FP16粗桶单调性。用同分热点验证正确性及原子争用。
2. 单行精确Radix基线：先验证FP32键、阈值更新、候选溢出重扫和最终同分前缀选择，再加GPU式FP16粗筛及桶缓存。
3. 完整L=65536、K=1024/2048单行实测；同时覆盖窗口、特殊值、K>2048、G>1与缓存外窗口。必须核对全部索引集合和确定性。
4. 编译代码、真实UB/W/D、spill/全局scratch、各轮候选数量和重扫次数、实际时延一起入证据包。不同轮的内部工作不能误算成独立host launch。
5. Prefill多行与Decode结构对照；完成正式依赖、默认编译后端及公共输入域验证后再提交完整实现准入。

全相等等最坏分布可能使阈值桶长期超过M，需要多次重扫和高争用原子操作；这不是算法错误，但性能必须单独测量。最后同键决议还可能增加一遍窗口扫描，不以平均桶大小推断最坏情况性能。

性能仍只评价延迟和相对CANN TopKV2加速比。正式对比使用同设备、同输入、同计时边界，包含窗口处理、填充、必要复制与输出转换。不能将此前bitonic微基准或官方Histogram样例耗时当作本Radix算子的性能，也不能先承诺其必然更快。
