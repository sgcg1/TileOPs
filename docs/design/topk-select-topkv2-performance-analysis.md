# TopKV2 性能原因与初版优化方向分析

日期：2026-10-30。

参考：[Ascend C 实现方案](./topk-select-ascend-c-implementation-plan.md)。本文是性能研究，不改变 TileLang 主仓交付路线，不修改算子实现。

## 1. 结论与证据边界

主要差距在内核内部。初版使用的共享原子直方图、单线程桶扫描、候选溢出后的重扫以及较保守的行调度，是优先研究对象。官方公开实现展示了寄存器 SIMD 直方图、分块 UB 搬运和多种规模模板，可以作为技术参照。

必须区分三类证据：

1. 本机实测：同输入内核时间、桶分布、模型属性、任务类型、工作区申请。
2. 公开源码：官方存在的算法与优化机制。
3. 待验证因果：各机制对这次约 24.5 倍差距分别贡献多少，以及 Weekly 二进制实际选择的完整内部模板。

本次没有完成逐项消融，不能把各项收益相乘，也不能把公开源码直接等同于已安装二进制。

## 2. 同输入 Decode 实验：主要差距确实在内核

规格为 `[B,S,L,G]=[1,1,16384,1]`，K=2048，FP32，全窗口。输出预分配，初版直接调用已经实现的原始 TileLang 内核，不经过公共算子包装；没有修改算法。校验后再次 warmup 10 次，事件采样 50 次，另行 profiling 50 次。

| 实现 | 纯内核中位数 | 设备事件中位数 |
| --- | ---: | ---: |
| 初版 TileLang | 213.275 μs | 217.822 μs |
| 官方 CANN TopKV2 | 8.721 μs | 16.207 μs |

两边完整输入 SHA-256 相同：

`c59b9485e9750eaf04d4668934c0383510a15b2cc9365ef9c6c4b9eaf2bf7593`

内核延迟比为 `213.275 / 8.721 ≈ 24.46`。此前完整调用与静态模型事件的约 14.5 倍只能作为初步比较，本次内核对内核的结果更适合指导优化。事件与 profiling 来自独立采样，不通过相减精确估算包装开销。

初版原始任务表有 50 条 `KERNEL_AIVEC`，内核表有 50 条 `main_kernel`；CANN 有 50 条 `KERNEL_MIX_AIV`，内核表有 50 条 TopKV2。初版 profiler 报告 ACL→NPU flow 关联警告，但底层任务及内核时间表均实际存在；未把警告或进程退出码当成采集成功的唯一依据。

## 3. 最重要的差异：直方图如何执行

### 3.1 初版逐元素共享原子加法

初版代码将 FP32 分数转换为有序 uint32 键，按字节构造 256 桶直方图。SIMT 线程对共享 `hist[digit]` 调用 `T.atomic_add`。

这不是错误算法，但当大量值落入少量桶时，同一桶更新形成依赖和竞争。不能把 128 个 SIMT 线程理解为 128 次桶更新必然同时完成。

同一 Decode 输入的第一轮，最大四个桶计数为：

`4691、4620、2360、2325`

这四个桶占 16384 个输入的约 85.4%。因此，“256 桶应该能均匀分流原子操作”不符合当前输入。FP32 有序键的最高字节主要区分符号和指数，不能期待对常见分数分布均匀分桶。

### 3.2 官方公开实现使用 SIMD 直方图

官方 `radix_sort_topk_b32.h` 的 `GetCumSum` 使用寄存器向量装载、位移、掩码筛选和 `Reg::Histograms`，最终将累计直方图存回 UB。它表达的是一批元素的向量统计，而不是让每个线程争抢共享计数器。

这是解释差距的强候选机制，但尚未通过指令计数或消融证明本次二进制中的确切收益。不能据此给出“换成 Histograms 就必然提升若干倍”的保证。

初版还由 thread 0 串行遍历 256 个桶来确定阈值和偏移。这个阶段存在串行依赖；后续应评估向量累计和／并行扫描，而不是仅增加 SIMT 线程数。

## 4. 方案 D3 得到了针对本输入的支持

用原始输入在 NPU 上转换 FP16，仅观察粗桶；原始 FP32 分数保留不变。对比结果如下：

| 第一轮粗桶方式 | 阈值桶候选数 | 2048 条缓存能否容纳 |
| --- | ---: | --- |
| 初版：FP32 有序键最高 8 位 | 4691 | 否 |
| 方案 D3：FP16 有序键最高 8 位 | 835 | 是 |

FP16 粗桶之上的元素有 1767 个，仍需从阈值桶精确选择 281 个。835 个候选必须继续按原始 FP32 完整键细化，不能直接按 FP16 值决定最终集合。

FP16 高字节包含较多与该数值区间有关的有效分组信息，因此在这份输入上比 FP32 高字节更细。该输入上粗桶编号与 FP32 精确顺序的单调性检查通过。

初版实际边界链为：

`16384 个输入 → 4691 个边界候选 → 25 个边界候选 → 剩余配额归零`

第一轮有直方图统计和候选收集两次整行遍历。由于 4691 超过缓存容量，第二轮又走两次整行遍历；随后才使用 UB 中的候选。这里是源码可确认的全行访问路径，不等同于四次都从 HBM 取数，Decode 可能命中缓存。

这支持优先实验 D3，但有四个限制：

- 候选数不是常数上界。全同分、FP16 上溢形成的大桶等仍可能留下整行候选，D4 溢出重扫必须保留。
- 本次只验证这一份有限随机输入，未关闭舍入边界、NaN、Inf、±0、上溢／下溢的完整单调性与全序验证。
- 重扫时必须同时保留粗桶条件和 FP32 前缀条件，不能把其他粗桶重新纳入候选。
- 多一层粗筛有转换和统计成本，不能断言它对所有输入都比直接 FP32 radix 更快。

本实验只是分桶诊断，没有实现完整的新内核，也没有得到 D3 路线的端到端加速比。

## 5. UB、数据搬运和并行分工

官方公开模板显式使用 `DataCopyPad`、UB 队列和局部分块计算；适合时调用局部 `AscendC::TopK`，配置为 RADIX_SELECT。初版则在 SIMT 阶段直接索引 GM 输入，主要用 UB 保存直方图和边界候选。

优化重点应是“批量搬进 UB、批量向量计算”，而不只是扩大 UB 分配。初版候选数组的 ping-pong 不是输入搬运与计算重叠的证明；官方队列的存在也不能单独证明发生了有效双缓冲重叠。两者都需要时间线验证。

初版调度固定 `workers=min(rows,32)`：Decode 只有一个 worker，Prefill 最多 32 个。CANN 三组模型及 profiling 均显示 blockDim=56，但 56 是启动块数，不证明每个块均有等量有效计算，更不能证明 Decode 有 56 个核合作处理同一行。

公开 host tiling 实现会按行数、L、K、dtype、UB 等选择单块、单核分块、跨核及归并等模板。它不是一套固定调度覆盖所有规格。确切的本机模板和分行参数尚未从二进制中还原：调试编译命中了缓存，日志没有给出数值 tiling；目标文件符号也没有暴露模板类名。没有将这一项写成已证实结论。

另外，自建模型的编译缓存显示 CANN 申请工作区：Decode 16,826,368 B，Prefill K1024 为 17,235,968 B，K2048 为 17,293,312 B。这些是总申请量，不能全部归为算法 scratch，也不能据此反推出内部缓存布局。

## 6. 对参考方案的具体取舍

| 方案条目 | 研究结论 |
| --- | --- |
| D1 单行单核 | 适合作为 Prefill 起点；Decode 应单独评估行内并行，不能只在“UB 装不下”时重新考虑。性能版本也不应把 32 workers 固定为最优。 |
| D3 FP16 粗筛 | 本次候选从 4691 降到 835，值得做第一个算法实验；仍需完整正确性与延迟验证。 |
| D4 有界缓存 | 保留完整计数和溢出重扫，这是正确性要求；但它不是唯一可行的空间设计，分块候选、全局 scratch 等也可按预算比较。 |
| D5 同分前缀和 | 保留确定性要求；跨分块必须累计之前同分数量并保持绝对索引逻辑顺序。单块扫描复杂度不能代表整行同分处理总成本。 |
| D6 官方 TopK | 作为局部技术参照，不能直接替代完整窗口与确定性契约；本次研究不改变主仓 TileLang 交付范围。 |
| D10 C=2048、57 KiB | 可作初始预算，不能当作真实 UB 占用。K>2048 的完整合法域也要有分块输出等明确设计。 |
| M6 性能 | 当前已有条件受限的官方 TopKV2 延迟基线；后续按同输入、同内核计时比较。文档中的 MFU 未决项不应阻碍当前延迟研究，也不据此宣称达标。 |

建议实验顺序为：先确认主仓 TileLang 对寄存器 SIMD 直方图／扫描的表达及降低能力；对同一内核做逐项对照，依次验证 SIMD 统计、D3 粗桶、UB 分块搬运，再分别研究 Prefill 的 worker 数与 Decode 行内并行。不能用 `tilelang-ascend` 仓的能力代替主仓验证。

## 7. 不应作出的推论

- 不能认为 TopKV2 的优势来自 Cube 矩阵计算，本次是 AIV 任务。
- 不能认为 `sorted=false` 就没有任何局部排序；它只是不要求最终输出按分数排序。
- 不能认为 FP32 输入多就代表浮点 FLOPs 多；键变换、直方图、比较和索引操作是主要工作之一。
- 不能认为 CANN 已接近硬件带宽上限。按输入加 values/indices 输出的最低逻辑字节数估算，两组 Prefill 约为 175 GB/s；这不是实际 HBM 流量，也不足以判定瓶颈。
- 不能把更严格的 NaN／同分语义开销直接当作 24.5 倍差距的解释，需要单独消融。
